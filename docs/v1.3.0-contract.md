## 2. Scope lock — exactly two features

`v1.3.0` ships **two** features and nothing else:

1. **Provisional (speculative) streaming for tool-enabled turns.** Text produced by a
   tool-enabled model round is sent to the browser as it arrives and is *deterministically
   discarded* when that round turns out to request a tool, or when the turn fails. This
   **replaces** the v1.2.0 buffering of tool-enabled rounds. There is no feature flag, no
   toggle, and **no buffered fallback**: a turn is either progressive (provisional) or it
   fails.
2. **Read-only, bounded spreadsheet ingestion.** `.csv` (steps 68–72) and `.xlsx`
   (steps 73–80) become uploadable single-document attachments through the existing
   `POST /api/files` pipeline, with hard extraction bounds and explicit partial-coverage
   reporting. Nothing is written back; there is no formula evaluation.

Explicitly **out of scope** (do not add, do not "prepare for"): `.xls` / `.xlsm` / any
macro-enabled or legacy Excel format, OCR, formula execution, multi-file or multi-document
uploads, RAG, new tool types, parallel tool calls, offline/bulk processing, persistence,
authentication, feature flags, `.csv`/`.xlsx` inside `fetch_url`, or any change to
`AI_*` configuration beyond what a step explicitly adds.

## 3. Invariants carried over unchanged

Every one of these stays true on every step of this phase; a step that breaks one is a
STOP condition:

* Tools remain **opt-in and off by default**, validated before execution
  (`web_search` 1 / `fetch_url` 2 / `calculator` 3 executions per turn,
  `MAX_TOOL_EXECUTIONS_PER_TURN = 3`, `MAX_MODEL_ROUNDS = 4`, strictly **sequential**,
  one tool call per round — see [Tool execution limits](architecture.md#tool-execution-limits)).
* Untrusted document, page and tool text never enters the conversation at **system**
  priority; server-authored messages stay ahead of the conversation
  (runtime context → tool guidance → document policy), document content is a `user`
  message inside `<document>` delimiters.
* `[N]` source ids come from harness metadata, never from remote content
  (see [Tool-call compatibility](architecture.md#tool-call-compatibility)).
* No secrets, keys, raw error details, file paths, file contents, fetched URLs, page
  text, snippets or DNS data in logs or in browser-visible telemetry; tool lifecycle
  events carry names and counts only.
* `fetch_url` destination policy stays as documented
  ([Fetch URL and SSRF](security.md#13-fetch-url-and-ssrf)).
* Temporary uploads stay inside `AI_UPLOAD_DIR`, always cleaned up
  ([Path safety in cleanup](security.md#2-path-safety-in-cleanup)), and every extractor
  path keeps its bounds.
* Markdown stays rendered with raw HTML disabled and sanitized by DOMPurify.
* No version bump, tag or release until step 86.

## 4. Streaming baseline as implemented today (`v1.2.0`)

`POST /api/chat/stream` emits, in this order, with these payloads (`text` values are
always null-character-sanitized by `sanitizeSseData`):

| Event | Payload | When (current code) |
|---|---|---|
| `start` | `{ model: string, context?: ContextTruncationMetadata }` | Once, after the request is validated and budgeted. `context` is present **only** when the document was actually truncated. |
| `delta` | `{ text: string }` | Every forwarded text chunk, including a **whole buffered tool-enabled round flushed at the end** as one delta/done sequence. |
| `tool_start` | `{ name: string }` | After the call's arguments validate, immediately before execution. |
| `tool_end` | `{ name: string }` | Only when the execution **returned**; a failed execution never emits it. |
| `sources` | `{ sources: Array<{ id: number, title: string, url: string }> }` | Cumulative list for the whole turn, re-emitted after each completed tool. |
| `done` | `{}` | Successful terminal. |
| `error` | `{ code, message, detail? }`, or `{ message }` only on the raw no-tools parse-error path | Failure after headers were sent. Terminal. |

Current terminal and transport facts that the new contract must keep straight:

* Every **tool-enabled round is buffered** by the orchestrator: its text deltas are held,
  then either discarded (a tool call was found) or flushed at the end as a single
  `delta`/`done` sequence. Only a **no-tools pass-through** and the **forced final
  no-tools round** stream live.
* Upstream transport EOF without a provider `[DONE]` becomes an SSE `error` event
  (`"Stream ended without [DONE]"`) on the no-tools path, and an
  `INVALID_PROVIDER_RESPONSE` `AppError` on the orchestrated path — the same code as any
  other malformed provider response. Step 58 gives every completion failure (truncation,
  content filter, unknown reason, contradictory `finish_reason`, missing reason, missing
  marker) its own typed parser event, and steps 62–63 carry one stable code and one
  payload shape to the browser on **both** paths.
* The browser (`frontend/src/services/chat.ts`) currently **treats transport EOF as
  success**: when the stream ends without a `done`/`error` event and without an abort it
  calls `onDone()` (`StreamCallbacks.onDone`) exactly once, and it **silently ignores any
  unknown `event:` name**. Both facts are locked by colocated tests and are deliberately
  changed by step 63.
* Once headers are sent the route cannot return an HTTP status: failures are logged once
  and delivered as an SSE `error` event carrying the stable `code`.

## 5. v1.3.0 SSE event contract

New in `v1.3.0` (three events, all new names, all additive for clients that ignore
unknown events):

| Event | Payload | Contract |
|---|---|---|
| `preview_delta` | `{ roundId: number, text: string }` | Provisional text of one **tool-enabled** model round, emitted as the chunks arrive. Never a whole-round flush. |
| `preview_commit` | `{ roundId: number }` | The provisional text of `roundId` is authoritative: it becomes the answer. Emitted after the last `preview_delta` of that round and before `done`. |
| `preview_discard` | `{ roundId: number, reason: 'tool_call' \| 'error' }` | The provisional text of `roundId` must be removed from the UI. `tool_call` precedes the `tool_start` of that round; `error` precedes the `error` event. |

All other events (`start`, `delta`, `tool_start`, `tool_end`, `sources`, `done`, `error`)
keep the exact payloads listed in section 4.

### Identity and ordering

* `roundId` is a **one-based, strictly increasing** integer per HTTP request, assigned by
  the backend to each model round in the order the rounds run. It is not a request id, not
  a message id, and not a browser id. Rounds never overlap, so `preview_delta` of round
  `n + 1` never appears before `preview_commit`/`preview_discard` of round `n`.
* The browser's **generation guard is separate, local and independent**: the frontend
  tags each `streamChat` invocation with its own generation counter and drops events from
  a superseded stream. Nothing in this contract requires the backend to know about it, and
  no backend event may be used as a generation token.
* The provisional text of a turn is a single logical buffer: the browser shows the
  concatenation of the `preview_delta` texts of the *current* round only.

### Which text travels on which event

* `delta` is used **only** for text that was never provisional: the no-tools pass-through
  and the forced final no-tools round (`delta` never needs a discard).
* `preview_delta` + `preview_commit` are used for a tool-enabled round: when that round
  ends with plain text, its text is authoritative and is **not** re-sent as `delta`.
* There is no mode that buffers a tool-enabled round in order to emit it later as
  `delta`. A request with every capability off keeps the pure no-tools path
  (`start` → `delta`* → `done`) unchanged.

### History durability

* Preview text is **outside durable history** (the assistant message the browser keeps in
  state / `localStorage`) until a successful turn terminal.
* `preview_commit` moves the text into a *pending committed* UI state: it stays in the
  live preview area, not in durable history, and must still be dropped if the turn later
  fails.
* Only `done` makes the assistant message durable (text + `stopped?` flags + `sources`).
* A discarded preview never enters history, and never enters the `messages` array sent on
  the next turn.

### Terminal rules

* A **successful** turn ends with **exactly one** `done`, and no `error`.
* A **failed** turn emits **exactly one** `error` and **no** `done`, as far as the socket
  allows; after `error` the backend closes the stream.
* A client disconnect may deliver **neither** terminal: the backend stops upstream work
  silently and the browser stays in the stopped state (as today).
* `tool_start`/`tool_end`/`sources` never appear after a terminal event.
* Transport EOF is **not** a server terminal event in `v1.3.0`: the browser must treat an
  unterminated stream (no `done`, no `error`, no abort) as a failure and must not commit
  the preview as a completed answer.

### Message shape — the prompt-cache invariants

`routes/chat.ts` builds the provider request with the local `buildProviderMessages()`
helper, in this order:

1. server-authored `system` messages from `buildServerSystemMessages()` — runtime context,
   then tool guidance, then the document **policy** message;
2. the document **content** as a `user` message (untrusted, `<document>` delimited), only
   when a document is attached;
3. the browser conversation history in order, newest user message last;
4. during orchestration only: each round's internal `assistant` tool-call message followed
   by its matching `role: "tool"` result, appended **after** the conversation.

A cache-aware orchestrator (steps 61–63) must keep all of that byte-stable:

* the server block stays first, stays identical across the rounds of one turn, and never
  moves below the conversation;
* the conversation prefix stays identical between rounds: nothing is inserted between the
  harness block and the conversation, nothing is re-serialized or reformatted, and tool
  history is **appended only** — `v1.2.0` reuses one working array and appends each round's
  pair to it in place, which is what makes the earlier prefix reusable at all;
* assistant tool-call messages stay in object form (never stringified) and carry **no**
  `content` field — the buffered filler text of a tool round is discarded and never echoed
  to the provider. Phase 4 must not change that either: step 61 states that no speculative
  text may enter `workingMessages` or be sent back to a provider, so only the real
  OpenAI-style assistant tool-call and tool-result messages are ever appended;
* internal orchestration messages never surface as browser-visible text and are never
  returned to the browser as history.

`chatOrchestrator.streaming-baseline.test.ts` locks this shape (append-only prefix, tool
pair position, no `content` on the tool-call message, and one shared working array per
turn) so a cache-aware rewrite that reshuffles or rewrites the prefix fails loudly.

## 6. Provider completion vs `[DONE]`

The upstream completion signal and the `[DONE]` marker are two different things. In the
target contract, a round's provisional preview may only be **committed** when the round is
known to be a clean, complete, tool-free final answer:

| Upstream `finish_reason` | Tool fragments in the round | Required handling in `v1.3.0` |
|---|---|---|
| `stop` | none | Normal completion. If tools are still attached and this is a tool-enabled round: commit the preview and end the turn. If it is the no-tools path: `delta`/`done` as today. |
| `tool_calls` | ≥ 1 valid, fully accumulated call | Commit is **forbidden**: discard the preview (`reason: 'tool_call'`) before validating and executing the tool. |
| `tool_calls` | none (contradictory) | Contradictory state: must not commit preview; existing safe error path (`TOOL_CALL_*` / malformed-response handling). |
| `length` | any | Truncated output: must not commit preview as a complete answer; surface a stable error, never a silent success. |
| `content_filter` | any | Same as `length`. |
| unknown / unrecognized | any | Treat as unproven: must not commit preview. |
| absent / `null` in every chunk, but `[DONE]` present | none, plain text only | **Documented compatibility exception** (see below). |

Baseline note (why step 58 exists): `SseParser` currently reads `finish_reason` **only**
to detect `"tool_calls"`. `"stop"`, `"length"`, `"content_filter"`, an unknown string or a
missing `finish_reason` are all indistinguishable today — the parser only emits
`{ type: "done" }` at `[DONE]`. This is locked by
`backend/src/provider/__tests__/providerStreamContract.test.ts`.

**Documented `[DONE]`-without-`finish_reason` exception.** A server that sends `[DONE]`
after plain-text chunks with no `finish_reason` anywhere in the stream is accepted as a
normal completion **only** when all of these hold:

1. `[DONE]` was actually received (transport EOF without `[DONE]` is never a completion);
2. the round produced zero tool-call fragments (`id`, `function.name`,
   `function.arguments`, or an `index`-keyed `delta.tool_calls` entry);
3. the text is ordinary assistant text (no harness-owned boundary marker);
4. the round is either the no-tools pass-through or a forced final no-tools round — i.e. a
   round where a tool call was structurally impossible.

Any other shape (missing `finish_reason` **and** tools attached, or **any** tool fragment,
or a `[DONE]`-less stream) must not commit a preview and goes through the existing error
path.

## 7. Legal and illegal event sequences

`T` = `tool_start`/`tool_end`/`sources` triple. `P(...)` = one or more `preview_delta`
with the same `roundId`.

| Scenario | Backend → browser sequence (`v1.3.0`) | Terminal | Notes |
|---|---|---|---|
| No tool enabled (all capabilities off) | `start`, `delta`*, `done` | `done` | Unchanged from `v1.0.0`/`v1.2.0`; no preview events at all. |
| Tool enabled, model answers directly on round 1 | `start`, `P(r1)`, `preview_commit(r1)`, `done` | `done` | Round 1 text is provisional until `preview_commit`; never re-sent as `delta`. |
| Tool enabled, round 1 requests a tool, round 2 answers | `start`, `P(r1)`, `preview_discard(r1,'tool_call')`, `T`, `P(r2)`, `preview_commit(r2)`, `done` | `done` | Discard happens **before** validation/execution, so no preview survives into a tool round. `sources` is inside `T`. |
| Tool enabled, three tools then the forced final round | `start`, (`P(ri)`, `preview_discard(ri,'tool_call')`, `T`)*3, `delta`*, `done` | `done` | The forced final round runs with no tools attached, so its text is authoritative from the first chunk (`delta`, never preview). |
| Tool execution fails | `start`, `P(r1)`, `preview_discard(r1,'tool_call')`, `tool_start(n)`, `error` | `error` (no `done`, no `tool_end`, no `sources`) | Same rule as today: a tool that throws after `tool_start` never gets `tool_end`. |
| Preview text then turn failure | `start`, `P(r1)`, `preview_discard(r1,'error')`, `error` | `error` (no `done`) | `preview_commit` must not precede a turn failure. |
| Mid-turn provider error (no preview emitted yet) | `start`, `error` | `error` (no `done`) | |
| User Stop / New conversation / page close | `start`, `P(r1)`…, stream cut | none | Silent on both sides; upstream request aborted; the browser must not commit the preview. |
| Transport EOF with no terminal event | `start`, `delta`… / `P(r)`… then EOF | **not a success** | Today (v1.2.0) the browser calls `onDone()`; step 63 turns this into a failure. Distinguish EOF from a server `done` in every layer. |

Structurally **illegal** (a reviewer must reject an implementation that can produce them):

* two `done` events, or `done` and `error` in the same turn;
* any `delta`, `preview_delta`, `preview_commit`, `preview_discard`, `tool_start`,
  `tool_end` or `sources` after a terminal event;
* `preview_delta` after `preview_commit`/`preview_discard` for the same `roundId`;
* `preview_commit` or `preview_discard` for a `roundId` that never had a `preview_delta`;
* `preview_delta` for two different `roundId`s interleaved, or a `roundId` that is not
  strictly increasing within a request;
* `tool_start` for round `n` before `preview_discard(n, 'tool_call')` when that round
  emitted a preview;
* `delta` carrying the text of a tool-enabled round (would mean a buffering mode exists);
* committing a preview (`preview_commit`) for a round whose upstream state is not clean
  per section 6;
* a fifth model round, or a fourth executed tool.

## 8. Two independent document truncation layers

Spreadsheet ingestion adds **no** new truncation layer; the two existing ones stay
independent and must both keep reporting coverage end to end (locked again by step 82):

| Layer | Where | Bound | Reported today |
|---|---|---|---|
| **Extraction** | `backend/src/extractors/*` (txt/md/pdf; CSV/XLSX in steps 69–78) | per-type extraction caps, applied while reading the file | `extraction.characterCount` + `extraction.warnings` in the `POST /api/files` response |
| **Context budget** | `backend/src/context/context-budget.ts`, applied by both chat routes before the provider call | `context.maxTokens` (1024 … 2 000 000) | `start.context` (`ContextTruncationMetadata`) only when the document was actually truncated; `DOCUMENT_CONTEXT_TOO_LARGE` / `CONTEXT_TOO_LARGE` when it cannot fit at all |

A file can therefore be extracted completely, truncated by its own extractor cap, and then
truncated again by the context budget. The extraction layer's partial-coverage signal must
survive to the browser even after context truncation, so a spreadsheet answer can state
that it covers only part of the workbook. Nothing about spreadsheets changes the tool
result budget (`context/toolResultBudget.ts`), which is a third, unrelated cap.

## 9. XLSX safety gate

XLSX support is **conditional**, not assumed. Steps 57 and 73–78 must prove, with executed
tests against adversarial fixtures, before any upload path accepts a workbook:

* ZIP entry-name containment (CWE-22 inside the archive), entry-count, per-entry and total
  uncompressed size and compression-ratio bounds, no zip-bomb / no symlink-ish entries;
* OOXML package validation (mandatory parts, workbook type, shared-strings bounds) and
  **rejection of macro-bearing and legacy formats** (`.xlsm`, `.xlsb`, `.xls`);
* bounded, **killed-on-timeout** child-process isolation with enforced CPU/memory/size
  budgets and reliable cleanup on every exit path;
* a streaming worksheet reader that never materializes the whole workbook.

If any of these cannot be proven, the answer is **NO-GO**: XLSX is dropped, `v1.3.0` is
blocked or re-scoped, and CSV/`.csv` only may still ship. Never ship an unsafe parser,
never relax a bound to make a test pass, and never proceed to a release step after a
NO-GO.

* `backend/src/orchestration/__tests__/chatOrchestrator.streaming-baseline.test.ts` —

  reasoning in steps 61–63 depends on.

Rules: no real provider, no Tavily, no network, no clock, no randomness in fixtures; the
same fixture must produce byte-identical frames every run. No fixture asserts behavior a
later step has not implemented yet — the suite must never contain a knowingly failing
test: characterization tests assert what `v1.2.0` does today and name, in a comment, the
step that is allowed to change it. Existing orchestrator-level fakes
(`createRecordingClient`, `chatChunk`, `textEvent` in
`backend/src/orchestration/__tests__/`) stay where they are and may adopt the shared
module in a later step.
